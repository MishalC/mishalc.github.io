Delivery and releases

Project Lead for the engagement from May 2026, with 11 engineers across three squads by October. This page shows how releases ran, how reports reached the right team, and the operating model behind both.

  • Each line is a step in the flow
  • The moving dot carries one piece of work through the flow. A step lights up when the work reaches it

Release tracking

Problem
We released to production on most weekdays: over 3,000 tickets from July to October, about 36 a weekday. People who reported bugs could not see when their fix went out: the work was tracked in Linear, and they had no Linear seat.
Solution
Release tracking posts AI-written notes in Slack for each production release, and replies in the reporter’s own thread when their issue reaches production. They hear back without a Linear seat.

Live from July 2026, with over 100 releases tracked by October 2026. A GitHub Actions workflow, written in YAML, uses the Linear API, a Slack incoming webhook and a Slack bot. It runs only once a production deploy is confirmed live, and splits long notes into a thread. It did not deploy anything.

  1. GitHubProduction deploy confirmed live
  2. GitHubGitHub Actions workflow (YAML) runs
  3. LinearLinear API creates the release
  4. AILinear’s AI writes the release notes
  5. SlackIncoming webhook posts the notes
  6. LinearReads the Slack link on each issue
  7. SlackSlack bot replies in the reporter’s thread

Triage and routing

Nothing changes in Linear until a person approves it.

  1. SlackSomeone reports an issue and tags the agent
  2. AILinear’s Slack agent makes a structured ticket
  3. LinearTriage suggests routing from AI guidance I set
  4. AIDaily triage routine checks for duplicates
  5. YouA person reviews the proposed actions
  6. AITriage skill applies what was approved
  7. LinearTicket goes to the owning team

  • Operating model

    Co-owned the move to Kanban squads with engineering leadership from April 2026: four squads, then three from August. Configured the tracker with a 12-state workflow and labels for severity, QA routing and feature flag lifecycle, reviewed the readiness and done-definition documents, and standardised estimation on T-shirt sizes.

    Tools: Linear

  • Planning

    Facilitated the bi-weekly engineering planning meeting, using the internal planning dashboard I built (AI-assisted), which shows shipped, in-flight, stuck and hygiene work per squad.

    Tools: Linear, You

  • Release coordination

    Coordinated production releases with QA and engineering: go/no-go checks, release timing and go-live confirmation to the team. Wrote test runbooks for the demo builds and tracked the merge of demo work back to the main branch, with owners and actions per pull request.

    Tools: GitHub, Slack

  • Delivery metrics

    Weekly reports tracked capacity against a 40-hour baseline and flagged burnout risk. Flow metrics per engineer and squad, throughput, cycle time and lead time, came from merged pull requests across the product repositories, through a dashboard I built (AI-assisted) and shared tracker views.

    Tools: Linear, GitHub
